### 10-1 [FIX] [P0] Dropping an `EventStream` must cancel the upstream request
- **Where:** `crates/llm-proxy-bridge/src/lib.rs`: `struct EventStream` (~842), `impl EventStream` (`cancel` ~911, `is_cancelled`), `StreamCancel`, `pump_events` (~751), `send_event`, struct doc ("Dropping it, or calling `EventStream::cancel`, cancels the upstream request") and module doc lines 17-19. Report row 11, gap 1.
- **Now:** there is no `impl Drop` in the crate. Dropping the `EventStream` drops the receiver, but `pump_events` only notices when its next `tx.send` fails, i.e. on the next upstream event, or when `cancel()` fires the `watch`. On a stalled upstream the request keeps running until the 60 s default idle timeout (`provider_config.rs` `default_idle_timeout`) and settles as an idle timeout rather than `ClientCancelled`.
- **Wanted:** plan: "dropping or cancelling settles as ClientCancelled".
- **How:**
  1. Add a field `ended: AtomicBool` to `EventStream` itself (not to `StreamCancel`), set to `true` in `next` / `next_blocking` when the channel returns `None` because the sender closed (pump finished normally) and not because of a cancel.
  2. `impl Drop for EventStream { fn drop(&mut self) { if !self.ended.load(Ordering::Acquire) { self.cancel(); } } }`. `cancel()` is synchronous, lock-free (`AtomicBool::store` plus `watch::Sender::send_replace`), so it is safe in `Drop` from any thread, including a tokio worker.
  3. Fully drained streams must stay `Completed`, not become `ClientCancelled`: verify with the test below. If the engine records the completion only when the pump observes `tail.next() == None` and a consumer drops right after the terminal event, `ended` is not yet set. In that case set `ended` also when the consumer receives an event that is a terminal one (the core `MessageStop`-equivalent, tag visible through `serde_json::Value`'s single key; check `CoreEvent` for the terminal variant) so that "read everything, then drop" never cancels.
  4. Fix the docs listed in 10-4 only after this lands.
- **Test:** `crates/llm-proxy-bridge/tests/surface.rs` (reuse `streaming_bridge`, `spawn_stalling_sse_upstream`, `stream_body`, `assert_settles_client_cancelled`):
  - `dropping_a_stream_settles_client_cancelled_without_waiting_for_the_upstream`: `execute_stream` on the stalling upstream, read the first event, `drop(stream)`, then `assert_settles_client_cancelled(&bridge)` with its usual timeout, and additionally assert the elapsed time is well under the 60 s idle default (use a 5 s bound in the helper call; the upstream gap is an hour in `spawn_stalling_sse_upstream`).
  - `a_stream_dropped_before_the_first_read_is_cancelled`: drop immediately after `execute_stream` returns.
  - `a_fully_consumed_stream_that_is_dropped_stays_completed`: use the non-stalling streaming upstream; drain via `next()` until `None`, drop; assert the recorded usage rows contain a completion row and no `ClientCancelled` failure row. Also a variant that drops right after the last real event without polling to `None` (this is the case step 3 protects).
  - Before the fix the first two fail (no `ClientCancelled` within 5 s).
- **Done when:** the three tests pass; `grep -n "impl Drop for EventStream" crates/llm-proxy-bridge/src/lib.rs` has one hit.
- **Risk / notes:** the Python and Node `Stream` objects own an `EventStream` (`bindings/python/src/lib.rs` `struct Stream { inner }`, `bindings/node/src/lib.rs` `struct Stream { inner }`), so this single change gives both a real drop path: CPython drops the native object at refcount 0 (immediately for a temporary), Node drops it at GC finalization (not prompt, which is why 10-2 exists). No new public API.

### 10-2 [FIX] [P0] Node `for await ... break` never cancels (iterator has no `return()`)

- **Wanted:** "break or cancel to stop upstream" (README) and "dropping ... settles as ClientCancelled" (plan).
- **How:**

In `[Symbol.asyncIterator]()` return `{ next, return: async () => { await this._native.cancel(); return { done: true, value: undefined }; }, throw: async (error) => { await this._native.cancel(); throw error; }, [Symbol.asyncIterator]() { return this; } }`. Add `Symbol.asyncDispose` on `Stream` (`async [Symbol.asyncDispose]() { await this.cancel(); }`) for `await using`; guard with `if (Symbol.asyncDispose)` because older Node lacks it (define the method with a computed key only when the symbol exists, via `Object.defineProperty(Stream.prototype, Symbol.asyncDispose, {...})`).
  3. `index.d.ts`: declare `return(): Promise<IteratorResult<...>>` through the `AsyncIterableIterator` type for `[Symbol.asyncIterator]()` and the optional `[Symbol.asyncDispose](): Promise<void>`.
  4. `src/lib.rs` doc comments: replace "(or dropping)" with the true statements from 10-4.
- **Test:** `bindings/node/test/bindings.test.js`, helper-reuse from the cancellation tests at ~272 and ~334:

  - `an exception inside the loop body cancels as well` (`throw` in the body, caught by the test).
  - `completing the loop normally does not cancel` (`cancelled` stays `false`, no `ClientCancelled` row).
- **Done when:** the three tests pass.
- **Risk / notes:** `return()` awaiting `cancel()` is fine because `cancel` is synchronous in Rust; keep it async for API symmetry.
